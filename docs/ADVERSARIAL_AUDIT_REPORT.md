# Adversarial Architecture Audit — MHT Priorities and RB Master Specification

**Assessment date:** 2026-10-08  
**Repository state examined:** branch `main`, HEAD `99b9310` (`fix(physics): gate approximate gravity backend selection`), package/VERSION/changelog at 9.4.0, with an extensive pre-existing dirty worktree.  
**Purpose:** critically assess the 12 architecture-review priorities tracked in [`ARCHITECTURE_PRIORITIES.md`](ARCHITECTURE_PRIORITIES.md) against the RB master specification and the actual code/tests/docs visible in this workspace. This is a review report, not authorization to implement recommendations.

## 1. Executive assessment

The repo has substantial foundations: P4 extracted worker transport, population lifecycle and intelligence cadence; ControlProfile UI/state exists; approximate CPU gravity selection now uses a registry resolver; law relationships, module contracts and a provider-neutral compute-session prototype have unit coverage. These foundations do **not** amount to completion of the larger architecture proposed by the review or the master spec. Most significant target boundaries remain absent or only partially exercised in the real app.

**Highest-risk findings:**

1. **D4 is not consistently enforced.** Barnes–Hut/FMM use `resolveGravityBackend()` in `src/physics/solver.js`, but the WebGPU pre-pass is started directly by `computeEngine === 'gpu'` in `src/worker/physics.worker.js`. `gravity-gpu-prepass` is registered as accepted yet the runtime worker path does not call `stageGate`, `lawPlan`, or inspect `approximationGates`. The shipped default compute selection is GPU. This is a policy/runtime contradiction, not merely missing diagnostics.
2. **The saved-world boundary is not a replay/continuation boundary.** `worldSave.js` v1 captures particles, DNA, five law words, params, selected runtime knobs, tick and some civilization/Codex state; it omits PRNG state, launch seed, worker/subsystem/cadence clocks and many mutable registries. Restore does not return/adopt the saved tick in the main restore path. Undo de-duplication's `sameWorldFingerprint()` also omits particle contents, DNA, runtime and world size, so distinct states can compare equal if its included summary keys match.
3. **“SimulationRuntime extraction” is overstated if interpreted as a runtime/coordinator boundary.** Three valuable P4 modules exist, but `main.js` remains a large boot/render/event/save orchestrator and still owns composition/order; worker bridge consumes mutable `runtimeConfig` and calls solver imports directly. The documented e2e proves selected behavior, not module ownership, full boot/disposal parity, or cross-browser parity.
4. **The new contracts are mostly not the production composition.** `ComputeSession` is not wired into `main.js`; its worker adapter protocol does not match the actual worker reply (worker replies lack the adapter's expected `seq`, and the bridge does not use this adapter). Module catalog planning is tested, but the catalog is data and does not compose/start the live app or enforce private-import boundaries.
5. **The source artifact for the external review is missing here.** No `.mht`/`.mhtml` exists in the workspace. The 12 row descriptions are therefore taken from the checked-in derived tracker [`ARCHITECTURE_PRIORITIES.md`](ARCHITECTURE_PRIORITIES.md), not independently compared against the original saved conversation. This is a material provenance limitation: wording, caveats, and any other MHT observations not copied into that tracker cannot be certified by this pass.

**Overall:** treat the MHT priorities as useful hypotheses and the RB master as a target design with recorded decision overlays—not as a verified architecture implementation. Keep exact-CPU/reference, parity, recovery and external-device claims narrowly qualified until the gaps below close.

## 4. Severity-ranked findings

### A-01 — GPU approximation registry is not the runtime gate (Critical / D4)

`src/physics/approximations.js` registers `gravity-gpu-prepass` as `accepted`, defines a `GRAV` tolerance, and its tests prove registry-helper behavior. `src/worker/physics.worker.js` nevertheless enters the pre-pass based only on `gpuReady && runtimeConfig.computeEngine === 'gpu'`; this path does not call `stageGate()` or check `runtimeConfig.approximationGates`. `runtimeConfig.computeEngine` and the launch default are GPU. By contrast, `src/physics/solver.js` resolves BH/FMM through `resolveGravityBackend()`.

**Impact:** D4's governance boundary can be bypassed by the default path. The registry's “registered + accepted + enabled” guarantee only governs the CPU-BH/FMM selector. `gpuActive` reports a buffer was returned, but does not report a registry decision or per-law gate result. A user can reasonably infer that an empty gate list means exact CPU, while it does not prevent GPU gravity execution. Also, a registered `bit-exact` classification plus `1e-4` force tolerance mixes exactness class and approximate tolerance; hardware/device-specific evidence and whole-runtime applicability are not implied by a registry schema test.

**Recommended action:** make the worker resolve a GPU stage gate using the same policy input and accepted gate ID before dispatch; default to CPU if gate disabled/unlisted; include resolved gate/backend/status in tick telemetry. Add worker-level tests proving empty gates skip GPU compute, explicit gate permits it, and fallback is visible. If policy intent was “GPU is an execution engine, not an approximation,” record a revised D4 and split compute selection from approximation approval. Do not silently weaken the existing decision.

### A-02 — Save and undo identity cannot support deterministic replay claims (High / MHT 4–5; master §§4.1, 4.4 and component 09)

`WORLD_SAVE_VERSION=1`. Capture includes particle and DNA copies, five law words, params, only `RUNTIME_KNOBS`, tick and selected civilization/Codex payloads. It does not capture `WORKER_SEED`/current `SplitMix32.state`, pending worker work, narrative PRNG state, intelligence/engine cadence/cache state, all world registries or launch/execution choice. Worker exposes RESTORE tick count, but ordinary `main.js` restore stops/restarts the worker and adopts particle/species/worldSize; the inspected restore path does not set main `tick` from the save. `restoreWorldState()` applies mutations to supplied targets rather than providing a fully validated staging/migration transaction.

`sameWorldFingerprint()` compares tick/count/species, civilization/Codex JSON, law words and world params—but not particle bytes, DNA, runtime knobs or world size. Two materially different worlds with same compared fields can therefore be treated as the same checkpoint by `createUndoRing.commit()`.

**Impact:** named world snapshots are useful save/restore snapshots, but not a deterministic continuation/replay log. Undo can suppress a checkpoint when omitted state changes. Tick display/telemetry may diverge after load, and interactions depending on random draw position/cadence cannot be promised reproducible. The master explicitly says deterministic continuation only when all mutable state is captured; current source does not meet that bar.

**Recommended action:** separate documented guarantees (`configuration`, `world snapshot`, `continuation`, `replay`) and encode them in schema. Include seed + PRNG state(s), current tick, worker/engine cadence and mutable registries for continuation, or label snapshot as non-continuable. Make restore validate/normalize into staging before mutating and then restore all clocks consistently. Define undo equality by state version/hash or complete captured-state comparison, then add regression tests varying only particle, DNA, runtime and worldSize.

### A-03 — Proposed ComputeSession contract is not the live execution path (High / master §§3.3, 4.4, 07)

`src/compute/computeSession.js` is instantiated only in tests/catalog, not `src/main.js`. The worker adapter test uses an injected fake protocol which sends `TICK_COMPLETE {seq, result}`; the actual worker posts `TICK_COMPLETE` with `tickCount`, duration, counts, GPU flags, no `seq`/`result`, and `workerBridge` sends `{type:'TICK', particleCount, dt}` without `seq`. The adapter's `source` payload is not how the actual worker accesses SharedArrayBuffer or DNA. Remote adapter posts a job to an injected URL but has no provider auth, session lifecycle, command validation/idempotency, stream/snapshot protocol, reconnect/keyframe or authority handoff; its capability flag says `authoritative:false` while generic session language says session owns ordered authoritative ticks. `dispose()` rejects queued items but does not cancel or fence an in-flight adapter tick.

**Impact:** unit coverage demonstrates an abstract contract, not compatibility with production transport; replacing the bridge with this adapter as-is would hang waiting for a sequence-bearing message. Provider-neutrality avoids premature vendor choice, but the port is not yet a remote simulation implementation or a complete secure protocol.

**Recommended action:** specify one concrete interface mapping from existing bridge to session (buffer ownership, tick/seq response, errors, stop/restart, config changes); integration-test that exact adapter against the worker protocol. Decide whether remote port is merely a sketch or a contract gate; if retained, define a versioned envelope, validation, acknowledgement and in-flight cancellation semantics, without implying provider/security completeness.

### A-04 — Module catalog validates metadata, not architecture isolation or app composition (High / MHT 1; master §§3.2, 3.4, 11)

`createCompositionPlan()` validates manifest IDs/semver, owners, declared ports/capabilities and graph cycles. `moduleCatalog.test.js` validates catalog plan, listed paths, every `src/` directory having some catalog entry, paths and declared contracts. There is no enforcement of private-import rules, source-import boundaries, singleton access, DOM reachability, ownership of writes at runtime, test coverage for every module, or schema migration implementation. Catalog module comments explicitly say it does not replace `main.js` boot; production never invokes `startComposition()` or `moduleCatalogPlan()`.

**Impact:** catalog/plan success can be mistaken for isolated modules or a functioning composition root. Current code still has direct imports across boundaries and mutable singleton access (e.g., worker bridge imports `runtimeConfig`). The acceptance claims in D5 (“module boundaries enforced by contracts”) exceed what these validators prove.

**Recommended action:** scope D5 honestly as catalog/contract metadata validation today. Add a source import-boundary checker only after a real module ownership map exists; distinguish runtime compositions from descriptive plan; wire composition only behind an approved staged migration and parity oracle. Require module-focused behavior/migration tests rather than catalog entry path existence.

### A-05 — Law graph is descriptive and incomplete as a planner input (High / MHT 2, 7; master §§3.2, component 05)

`lawOntology.js` explicitly says its relationship vocabulary does not gate/reorder solver behavior. `lawGraph.js` exports/inspects the graph and validates IDs/categories/state names/cycles; no execution-plan generator exists. The ontology adds high-priority records while unlisted relationship types remain intentionally absent. The records are law-to-law/state descriptions, not complete kernel manifests declaring actual read/write sets, stage ordering, cadence, backend support, allocation/error contracts or verified implementation binding. Validation checking the vocabulary does not ensure each claimed read/write matches implementation.

**Impact:** using this graph directly for execution order would infer too much from partial prose and could create unsafe reordering or parallel conflicts. “One authoritative schema” is not achievable simply by generating a graph from current records; schema ownership and semantic validation are prerequisites.

**Recommended action:** maintain separate identity metadata, behavior/kernel manifest and relationship graph until complete coverage/ownership is demonstrated. Add per-law implementation/test binding and compare declared vs measured access/order. Start planner at a bounded subset with differential tests; never let descriptive relationships reorder production execution implicitly.

### A-06 — P4 status can be green while the more important orchestration contract remains (High / MHT 1; master §§3.1–3.3, component 01)

The refactors are real extractions, not merely renamed files. `workerBridge.js` injects world state and consequences, `spawn/population.js` is reused from render and tick pathways, and `intelligenceCadence.js` owns cached metrics/death scan/adaptation. The extraction plan explicitly leaves boot, `applyPrimeWorldConfig`, render loop and wiring in `main.js`. Current source is 1,737 lines; the master component copies still describe 1,931 lines and an older baseline, while the plan inventory's 1,537/1,675-line figures are another snapshot. The facade modules also retain imports of `runtimeConfig` or solver-specific implementations, so narrow module ports and isolated composition have not arrived. `main.js` still seeds with `Date.now()` at boot and handles commands/restores/events directly.

**Impact:** reduced file size and injected contexts help reviewability, but do not alone establish single session ownership, lifecycle disposal, typed/versioned commands, idempotent command application, or no duplicate listeners. Reported e2e tests cover selected user paths, not all launch/settings/save/undo/repeated-reset semantics. Repeated `startPhysicsWorker()` calls terminate existing worker; that is a lifecycle choice to exercise under boot/restore races, not proof of idempotent app startup.

**Action:** specify what “SimulationRuntime” owns (session/world/cadence/transport/render lifecycle) independently of line-count goals. Add production boot/reset/restore/dispose tests and event subscription-count checks; list retained singleton/import edges as temporary exceptions. Reconcile line-count/ownership inventories before using them as risk estimates.

### A-07 — ControlProfile implements much of D1, but “atomic transaction” and user preview are stronger than evidenced (Medium-high / master §§4.1–4.2, component 02–04)

The current Easy profile is a meaningful recipe layer with per-surface `localStorage` mode, pure previews, canonical world/DNA targets and reverse projection. However, for world recipes the DOM displays old→new member values during `input`, then `change` emits `world:paramsPatch`; `main.js` loops over keys and re-emits `world:paramChanged` one by one. Each key updates state/emits `world:paramApplied`; a single final `world:paramsApplied` event summarizes. This is coherent UI behavior, but not an isolated transaction with one canonical delta, rollback, or single event. Undo relies on a time debounce of `world:paramChanged`, not a transaction ID. Species writes a whole recipe before one `dna:changed`, which is better grouped but still uses the shared mutable genome buffer.

The composite UI shows current values and a before→after preview, but applies on slider `change` without a separate confirmation for the recipe's multiple effects. `effect` is static text; e.g. the `scale` group includes `INITIAL_POP` and says it applies on next restart. That informs but does not establish the master requirement to make destructive/reseed consequences clear before apply. The world recipe declarations use normalized anchors; units/labels derive from metadata but Easy preview formatting prints label and number only, not units. `projectGroup()` averages per-member inferred t and marks customization by spread/out-of-span; for nonlinear interpretations or values near quantization/clamp boundaries, this is a display projection, not a unique inverse. `CUSTOMIZED_SPREAD` is an arbitrary policy threshold requiring UX review.

**Action:** describe D1 as implemented for current recipe UX, not as proof of transaction-service or full undo semantics. Add transaction IDs/one normalized delta and tests that assert observers never see a partial group. Explicitly surface whether each affected member is live/restart/reseed and require confirmation only where truly destructive. Show units (or explicitly state normalized/derived values), and test mixed/manual values, rounding, clamps and preset launch defaults in real browser.

### A-08 — World parameter/DNA policies prevent count drift but do not establish semantic coverage (Medium-high / MHT 2, 7; master §§4.2–4.3, components 03–04)

`WORLD_PARAM_DEFS` has 149 records, DNA has 64 traits, and `paramAdditionPolicy.test.js` freezes counts at 149/64, requires a complete evidence record for non-empty additions, and checks recipe targets exist. Since `additions[]` is empty today, the policy passes vacuously. It does not currently assert that every one of 149 world parameters and 64 DNA traits has a named consumer, effect test, units, migration policy, or explicit reserved/UI-only classification. `param-addition-policy.md` says all those details are required for *new additions*; it does not satisfy the Master §03 requirement for every existing definition. World parameter definitions carry useful key/label/range/default/group, but source review did not find a complete schema-version/scope/mutability/owner/provenance record across all definitions. DNA keeps numeric IDs and `WORLD_PARAM_DEFS` is still a combined schema/default source, not split into schema vs world state.

**Impact:** count gates stop accidental growth, not dead parameters, missing consumer wiring, inconsistent unit interpretations, or incompatible save migration. A written “consumer required” policy is not a live static check of current definitions. Legacy fixed-width DNA makes silent index changes high impact.

**Action:** build a coverage inventory (every parameter/trait → consumer(s), test(s), serialization key/version, unit/default/range, and explicit status). Keep it generated or verified against source. Audit top risk items first (runtime-only vs world fields, DNA cache vs genome-only traits, and special-cased world keys); retain D2 approval for additions without misrepresenting it as full schema validation.

### A-09 — D6 is a defined P0 run, not complete browser-parity acceptance (Medium / master §5, component 08, decision D6)

The QA matrix records Chromium managed-preview passes (11/11 in one result block) but also explicitly says Firefox/WebKit, touch-device, screenshot gating and hardware-WebGPU parity remain open; one hardware test self-skips when WebGPU is unavailable. Screenshot tolerance is explicitly *proposed, not approved*. Coverage rows for law-grid interaction, browser save/undo/compare, drawer keyboard/touch and visual parity are pending or static-only. The recorded run is against HEAD `01b34c7` plus the then-current worktree; the present HEAD is `99b9310`, so it is not a direct validation of this exact source state. The original first-run matrix states 8/8; the subsequent 11/11 claims are historical evidence, but no corresponding artifacts were inspected here.

**Impact:** “D6 decision recorded” means a matrix was defined and a P0 Chromium subset was run; it does not mean all target browsers/devices or visual acceptance are done. A pass that self-skips hardware GPU validates skip annotation, not GPU fidelity. User-visible parity remains unproven for several essential flows.

**Action:** preserve run result and its tested commit provenance; append new run entries rather than editing historical results. Before release, execute Firefox/WebKit and coarse-pointer/touch; approve visual tolerance before it becomes a gate; run hardware WebGPU in suitable environment; add real-browser save/undo and law-grid flows. Never count skipped GPU fixture as parity pass.

### A-10 — Backend name, compute choice and actual path/status are conflated (Medium / MHT 6; master §§4.3, 06–08)

There are distinct controls `computeEngine` and `gravEngine`, and GPU contributes only gravity, with CPU remaining responsible for other law semantics. `workerBridge` emits backend telemetry from `message.gpuActive` / `gpuAvailable`; GPU fallback messages report CPU. But `runtimeConfig` says computeEngine defaults to GPU, launch UI advertises GPU, `approximations.js` currently documents registry-backed per-stage approximations and actual worker bypasses it. This means “GPU” is a capability/config preference, “WebGPU device available”, “pre-pass dispatched”, and “physics tick active backend” are not interchangeable. CPU-only laws may still be authoritative while gravity is GPU; saying the whole tick is WebGPU would be false.

**Action:** model requested compute preference, probed capability, actual per-stage backend and fallback reason separately. Send per-tick effective backend/gate to diagnostics; add tests for mixed stage (`gravity=gpu`, others CPU) and worker/device-loss transitions. Ensure launch help/default text agrees with policy and evidence; do not promote default acceleration based on the fact a probe exists.
